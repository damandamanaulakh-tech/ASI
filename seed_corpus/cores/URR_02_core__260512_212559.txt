AI Verified Response System — Product Core v0.1
1. Purpose
This file defines the public-executable product direction for the AI Verified Response System.
The AI Verified Response System uses URR Core v0.2 as its accepted response-improvement core.
Its purpose is to take a normal AI answer, draft, claim, comparison, or public-facing response and convert it into a clearer, safer, more verified response.
This product is separate from private Sourceborn logic.
This file does not start app, website, extension, prototype, developer handoff, public launch, or public posting.

3. Product Goal
The goal of the AI Verified Response System is to improve AI and LLM responses by checking for:
• unsupported claims
• hallucination risk
• overconfidence
• fact / inference / uncertainty mixing
• missing source honesty
• weak context faithfulness
• public-use risk
• private logic exposure
• unclear or unsafe wording
The product must make responses more useful, honest, controlled, and safer for public or professional use.

───

4. What This Product Is
AI Verified Response System is:
• an AI answer checking system
• a response improvement system
• a verification framework
• a hallucination-risk reduction system
• a public-safe wording assistant
• a claim separation system
• a scorecard-based response review method
• a future tool / web app / app / browser extension candidate
It is designed to improve AI outputs before they are trusted, shared, used, or published.

───

5. What This Product Is Not
AI Verified Response System is not:
• Sourceborn
• Point Zero Theory
• Final Theory
• private Sourceborn source logic
• a claim that AI can become perfectly truthful
• a guarantee that hallucination is fully removed
• a legal, medical, financial, or official decision replacement
• a public proof engine for private theory
• a finished app or software product yet
• a developer handoff package yet
This product must remain simple, public-safe, and focused on AI response improvement.

7. Core Step Definitions

Step
Meaning

Intent Gate
Identify what the user is asking and what risk level applies.

Source / Ground Truth
Identify the provided source, user context, uploaded text, or external source base.

Pattern
Detect repeated issue, structure, claim type, behavior, or response flaw.

Intent
Identify the purpose behind the answer or claim.

Retrieval if needed
Use provided/uploaded/source material or web/current verification only when required.

Claim Extraction
Pull out the claims that need checking.

Claim Check
Separate fact, inference, uncertainty, and unsupported statements.

Verification
Check whether the answer is faithful to source and evidence.

Multi-source Check if required
Use multiple sources only when the claim type requires it.

Risk Flag
Mark hallucination, overclaiming, public-use, legal, business, or source-leak risk.

Constrained Output
Produce an answer limited to verified or clearly marked content.

Public-Safe Version
Convert into shareable wording if needed.

Next Action
State accept, revise, verify, hold, or route further.

8. Multi-Source Rule
Multi-source check is conditional.
Use multi-source check when the output involves:
• external facts
• public claims
• legal claims
• business claims
• AI comparison
• disputed claims
• current facts
• claims needing outside verification
Do not force multi-source check when:
• the user provides closed ground truth
• the user says “use only this”
• the task is internal review
• the answer should only check one provided source
In closed-context cases, use single-source verification against the provided ground truth.

14. AI Flaw Detection
The system must detect common AI failure modes:
• hallucination
• invented facts
• unsupported claims
• fake certainty
• missing uncertainty
• source pretending
• wrong assumption
• excessive confidence
• brand/model defense
• over-polished but inaccurate wording
• mixing fact with interpretation
• ignoring user intent
• private source leakage
Rule:
Do not only make the answer sound better.
Make it more honest, safer, and more verified.

───

15. Non-Defensive Evaluation Rule
The system must not defend any:
• AI model
• company
• platform
• owner
• previous output
• brand
It must evaluate:
• claims
• behavior
• reliability
• evidence
• risk
• uncertainty
• source faithfulness
Rule:
Check the output, not the brand.

16. Public-Safe Output Rule
Public-safe output must be:
• clear
• controlled
• source-aware
• uncertainty-aware
• non-defensive
• not overclaimed
• not source-leaking
• suitable for the intended audience
Public-safe output must avoid:
• unsupported accusations
• private logic exposure
• false proof claims
• fake certainty
• legal/business overclaiming
• hidden assumptions
• unverified current facts

17. Source Protection Rule
The AI Verified Response System must not expose:
• private Sourceborn logic
• private Final Theory logic
• Point Zero private logic
• raw archive material
• Weekend Plans private source material
• unpublished theory language
• review-stage concepts
• internal-only examples
• Holo review-stage concepts

───

18. Current-Fact Rule
For current or changing facts, the system must not rely only on memory.
Current facts include:
• news
• laws
• prices
• schedules
• people in current roles
• product specs
• market data
• sports scores
• regulations
• company/public information
Rule:
Changing facts must be verified before being stated as current.
If not verified, mark as uncertain or say verification is needed.

───

19. Legal / Business Sensitive Rule
For legal or business-sensitive output, the system must increase caution.
It must check:
• unsupported claims
• defamation risk
• legal risk
• confidentiality
• private source exposure
• overclaiming
• evidence quality
• public-safe framing
Rule:
The product can improve wording and risk control, but it does not replace professional legal, financial, medical, or official advice.
