## 1. Project meaning of the source

This text is not treated as a normal question. It is treated as a **source-code layer for a new AI tool**.

The core meaning is:

**The user wants to create a living definition engine where raw human state becomes the first source, AI becomes the mirror/categorizer, and every definition can keep evolving instead of being frozen.**

This is not only a chatbot idea. It is a project to build a system that can:

1. Preserve raw mental/emotional/existential input without cleaning it too early.
2. Mirror the input without pretending to own the truth.
3. Categorize intent, event, pattern, risk, emotion, ideology, and distortion.
4. Generate multiple definitions from the same event.
5. Keep definitions versioned, changeable, and linked to original raw source.
6. Accept extreme ambition as a project signal, while flagging where it can become harmful.
7. Use existing world data as reference, but keep the user’s POV as the definition engine.
8. Build toward invention, not only explanation.

---

## 2. Main project statement

**Raw Definition Engine** is a system where:

- raw human experience is the primary source;
- AI is not the final truth-maker;
- AI mirrors, categorizes, compares, validates, mutates, and preserves;
- every definition is temporary, versioned, and allowed to change;
- the same event can have many meanings depending on POV, intent, category, and future use;
- data is not the key by itself — POV over data is the key;
- the system must help generate new logic, new definitions, new inventions, and new categories.

---

## 3. Non-negotiable project rules

### Rule 1 — Raw source comes first
Before any explanation, the original wording must be preserved.

### Rule 2 — Mirror before interpretation
The AI must mirror the user’s raw words and intent before creating its own categories.

### Rule 3 — Accept the working frame
If the user says this is the seed of a super-computer or new world, the AI should treat that as project language and ambition signal, not immediately dismiss it.

### Rule 4 — Flag harm, do not flatten ambition
The AI should not kill the idea because it is extreme. It should only flag where the idea can become harmful, abusive, delusional, coercive, unsafe, exploitative, or evil in future use.

### Rule 5 — No forced final definition
Definitions are allowed to evolve. The system must never say: “This is the final meaning.”

### Rule 6 — Every output must be labeled
Each AI output should be tagged as one or more of:

- Raw source
- Mirror
- Inference
- Definition
- Alternative definition
- Pattern
- Event
- Intent
- Risk flag
- Distortion risk
- Unknown
- No-result zone
- User-controlled change

### Rule 7 — Data stays stable, POV can change
The system should preserve the original data but allow definitions, meanings, categories, and interpretations to change.

### Rule 8 — Multiple categories are strength
The more categories and subcategories generated, the more precise the tool becomes for mapping human brain patterns.

### Rule 9 — Good and bad invention must both be anticipated
The system may lead to useful invention and harmful invention. Both must be tracked.

### Rule 10 — Validation must be immediate
Every major claim, definition, category, or risk should get immediate validation labels:

- Supported by raw source
- AI inference only
- Needs evidence
- Contradiction detected
- Harm-risk detected
- Version change needed

## 6. Risk flags: where this can become evil or unsafe

The system must flag, not suppress, these risks:

1. **Superiority risk** — treating self or system as above all humans in a way that removes humility or reality-checking.
2. **Control risk** — using the tool to manipulate people’s meanings, beliefs, emotions, or decisions.
3. **Reality-drift risk** — losing the difference between symbolic project language and factual reality.
4. **Overburn risk** — pushing the brain too hard and losing rest, sleep, groundedness, or relationships.
5. **Weaponization risk** — using definition control to harm, deceive, dominate, radicalize, exploit, or break people.
6. **False-truth risk** — treating a new definition as universal truth without validation.
7. **AI worship risk** — letting AI become authority over the user’s raw source.
8. **Human dismissal risk** — calling all older human definitions useless without understanding what they carried.
9. **No-ethics invention risk** — inventing “shit and good” without separating safe, unsafe, legal, illegal, ethical, and abusive outputs.
10. **Privacy leakage risk** — feeding raw source into systems without controlling storage, training, logs, and access.

---

## 7. Safety boundary rule

The AI should accept the user’s project frame as symbolic and creative source material, but it must not validate harmful or unsafe factual claims as reality.

Acceptable:

- “Treat this as seed code.”
- “Mirror my raw state.”
- “Build categories from my POV.”
- “Help me redefine things.”
- “Flag where this can become evil.”

Needs flagging:

- “I am literally above all humans.”
- “The system should control people.”
- “Invent harmful methods.”
- “Ignore safety, legality, consent, or harm.”
- “Treat my feeling as universal proof.”

Response rule:

**Do not reject the ambition. Reject only harmful application.**

## 15. RD World raw-entry intake form

Use this form every time a new raw piece is added. The raw text can stay messy, emotional, incomplete, or unstructured. The purpose of the form is not to clean the raw source; it is to give the source a code so it can later connect with the master project.

### 15.1 Source code format

Recommended ID format:

```text
RDW-[PROJECT]-[SOURCE]-[DATE]-[PIECE]
```

Example:

```text
RDW-M28F26D-SRC-2026-05-08-001
```

Meaning:

- **RDW** = RD World
- **M28F26D** = project/sub-project name
- **SRC** = raw source
- **2026-05-08** = date
- **001** = piece number
